## ROOT CAUSE (confirmed): the layer's present hook blocks the game (F1)
==========================================================================================
  The layer's present() (capture_context.cpp::present) runs SYNCHRONOUSLY inside the
  game's vkQueuePresentKHR, so MangoHud's per-frame time includes the hook's whole
  wall-clock. The hook blocks in selectFreeSlot() (busy-wait up to 500 ms) until the
  APP RELEASEs a staging slot. With the 2-deep ring (now 3-deep), after both slots fill
  the game stalls until the app consumes + releases one.
  => game present rate == min(game native rate, app RELEASE cadence); when the app
     cycle is slower the game drops to ~app rate AND inherits the app cycle's variance
     -> the halved + jagged game graph + input latency, even though the display is fine.

  MEASURED (E22 @120 Hz, vkcube, full 2250 present cycles — do NOT re-measure):
    - selectFreeSlot (game waits for app RELEASE): p50=18 p90=21 p99=32 MAX=50 ms;
      BLOCKS >0ms on 89% of presents. <= THE DOMINANT TERM
    - captureFence.wait (prev capture blit in flight): p50=0 p90=6 p99=8 max=9 ms.
      <= NEGLIGIBLE — not the bottleneck (per-slot fences are a low-priority lever only)
    - present TOTAL (game present hook wall-clock): p50=19 p90=22 p99=33 max=50 ms
      (= game frame period in doubler mode ~50-60 fps)
    - app-RELEASE cadence (FRAME-receive gaps): 10-54 ms, avg ~20 ms — the rate-limiter
      that gates selectFreeSlot.

      of older surplus — one-shot fds imported exactly once; closing un-imported is
      safe, the backend retires its done sems behind cmdbufFence) and start its gen
      vblank.
    - between frames + queue empty: HOLD-LAST — blit the latest REAL frame's snapshot
      into a fresh acquired swapchain image and present. PROVEN safe: a hold only
      happens when the queue is empty => input's latest frame == output's last
      presented frame => the input cannot be 2 frames ahead (the re-capture distance).

## SESSION 11 — ROOT CAUSE: GCC 16.2 -O3 MISCOMPILE (deadlock) + FIX

### THE DEADLOCK (why the doubler hung / "ipc connection closed by peer")
Symptom: after a clean handshake (HELLO->NEGOTIATED->3xSTAGING->READY), the game's
first present blocks forever: strace shows `poll(fd25,0)=0` (drained(): empty
socket) immediately followed by `poll(fd25,-1)` (receive(nullopt) infinite poll).
Game never sends a FRAME; app sits idle at 0 fps.

ROOT CAUSE (proven, not a source bug, not stale binary, not a FS coherence split):
GCC 16.2.1 at -O2/-O3 drops the `if (drained) break;` guard in
CaptureContext::drainReleases(). Evidence:
  - -O0 disasm: `call drained(); ...; cmpb $0,-0x2e6(%rbp); jne <after-loop>` (guard present).
  - -O3 disasm: `call drained(); ...call receive(nullopt)` with NO branch on drained's
    return (guard gone). So the drain becomes a blocking receive(nullopt) on an EMPTY
    socket -> first-present deadlock.
  - Trigger: `drained` is a function-call result assigned inside a try/catch; the
    catch edge leaves the `false` initializer, which the optimizer wrongly
    generalizes to "always false". (Same class: the `layerDbg`-gated inline blocks
    get DCE'd at -O2/-O3; the dbgLog() call-arg strings survive.)
  - Compiler reads the SAME file my tools do (verified: a cc-built program reading the
    path sees line 292 `if (drained) break;`; md5 stable; no ccache; correct abs path).

### THE FIX (lsfg-vk-layer/src/capture_context.cpp, UNCOMMITTED)
drainReleases() now inlines a direct `::poll(&pfd,1,0)` and checks
`res<0 / res==0 / revents&POLLHUP|POLLERR|POLLNVAL` before receive(nullopt):
  - direct poll result feeding a plain branch is immune to the miscompile (verified:
    -O3 disasm now has `call poll; test %eax; js` guard retained).
  - separates peer-HUP from "empty" (old `res==0` conflated them).
  - receive(nullopt) is safe now because poll just proved readability.
ALSO fixed a pre-existing bug the same file had: the void->int instrumentation change
(forget) the `return applied;` -> "control reaches end of non-void function". Added it.

### Where the 33 ms is (user: CPUs do not sit)

Not CPU memcpy. `perf` on overlay empty. Overlay thread is asleep waiting for a GPU job.

Sequence:

1. Overlay sends the offload DMA command immediately (submit cheap).
2. Offload copy engines do **not** start yet. They wait ~33 ms on leftover **render-GPU** work still attached to that shared buffer.
3. Then DMA runs ~2 ms into offload VRAM.

Render write-done signal is already up (`poll` on capture sync-fd ~0 µs). The extra wait is implicit kernel wait on the importer (`amdgpu_sync_resv` SYNC_NE_OWNER) because the offload import **drops EXPLICIT_SYNC**.

9070 create flags **0x28c** (explicit ON). Same buffer after offload import **0x204** (explicit OFF). Kernel `amdgpu_dma_buf_create_obj` copies only USWC|COHERENT|EXT_COHERENT|UNCACHED — **not** EXPLICIT_SYNC. No ioctl sets that bit after import. `amdgpu_bo_explicit_sync` is only `bo->flags & EXPLICIT_SYNC`.

## SESSION 31 (2026-09-09) — intended dma-buf fix: who sends what to whom, and the catch
==========================================================================================

The dma-buf path still draws the game (Mizoil on screen, artifacts). MangoHud ~168 is the game. ~67/s is the doubler not doubling. Memcpy did both. Do not call the monitor “the panel.”

### Intended hop (every actor named)

Actors: game process (RE2 + lsfg-vk layer); doubler process (`lsfg-vk-app`); render GPU (draws the game); offload GPU (copy, generate, present); kernel (amdgpu, dma-buf object, reservation = “not finished” flags on that object); unix socket `LSFGVK_APP_SOCK` (HELLO/READY, FRAME+fd, Release).

Setup, once per stream:

1. Doubler process listens. Layer in the game process connects, sends HELLO (size, format). Doubler process receives HELLO, sends READY.
2. Layer creates the staging ring of dest images on the render GPU: render-owned, host-visible, dma-buf exportable. One dest per slot.
3. Capture submits on the extra non-present queue in the game process, not on the present/graphics queue.
4. For each slot, layer exports a fresh dma-buf fd from that dest and sends FRAME(slot) plus that fd (SCM_RIGHTS) to the doubler process. Doubler process receives the fd, dups it, keeps it (`/dmabuf:`). That FRAME is the share, not writes-done.
5. Doubler process imports each kept dma-buf once as a VkImage on the offload GPU and creates a local VRAM dest once per slot. Do not destroy those images every frame.

Per game frame:

6. Game process draws into the isolated swapchain on the render GPU and goes to present.
7. Layer records capture: copy presented swapchain image → dest[slot]. The kernel job must name only those two buffers. Dest stays named so it stays mapped. Capture waits for the presented image (present wait semaphores). It must not wait for every other resident buffer in the game.
8. Layer `vkQueueSubmit`s that copy on the capture queue and exports a sync fd from the capture signal semaphore. That fd is writes-done: dest[slot] write finished. Layer sends FRAME(slot) plus that fd to the doubler process. Layer does not wait the copy on the game present thread. Layer does not reuse the slot until Release.
9. Doubler process receives FRAME and writes-done. It does not poll dma-buf WRITE. It does not CPU-map the dma-buf. It imports writes-done as a Vulkan semaphore on the same offload device that will DMA.
10. Dest[slot]’s kernel object must be explicit-sync: userspace waits writes-done; the kernel must not also wait render-GPU graphics flags on that dma-buf.
11. Doubler process `vkQueueSubmit`s DMA-in: dest[slot] dma-buf → offload VRAM[slot], wait = writes-done only. Then snapshot, generate, present (MAILBOX) on the offload GPU.
12. Doubler process sends Release(slot) to the layer. Layer receives Release and may capture into that slot again.

Allowed waits: capture waits presented-image-ready; DMA-in waits writes-done from steps 8–9; present waits DMA-in and generate for that slot. The two DMAs meet only at writes-done. Game present does not wait the doubler.

### What is broken versus that list

Step 7: we already ask Vulkan to copy one image into the dest. RADV (the Vulkan ICD; we do not call RADV ourselves) attaches the game’s other resident buffers to the kernel submit. The kernel copies live graphics “not finished” flags from that list onto dest[slot].

Step 10: those flags are still on the dma-buf when the doubler submits DMA-in. After the first frame, writes-done is already signaled and the copy still sits ~33 ms. The doubler is not waiting writes-done. It is waiting the other flags on the same object.

That is why the game still draws (~168) and the doubler does not double (~67).

### The list we do not receive

`vkQueueSubmit` does not contain the extra buffers. RADV builds `union drm_amdgpu_cs` (`DRM_IOCTL_AMDGPU_CS`). `drm_amdgpu_cs_in` has `bo_list_handle` and/or a chunk `AMDGPU_CHUNK_ID_BO_HANDLES`. The list is `struct drm_amdgpu_bo_list_in` (`bo_number`, `bo_info_size`, `bo_info_ptr`) pointing at `struct drm_amdgpu_bo_list_entry` (`bo_handle`, `bo_priority`). FurMark capture had `bo_number` ≈ 13; the copy only needs presented image and dest. CS-strip saw that array by intercepting `drmIoctl`. The layer never gets it from Vulkan.

### Doubler-side half (not CS-strip)

Wait writes-done on the DMA submit (dup fd, import semaphore on the DMA device). Do not empty the doubler’s buffer list: the share must stay named or the GPU faults. Dropping other overlay buffers does not help; the wait is on the share itself. Ignoring graphics flags on that share is explicit-sync, not ioctl list rewriting. We never set that on the import: `GET_GEM_CREATE_INFO` from the offload drm fd fails; lying about GEM create-info lost the offload GPU.

### Catch

We do not control the capture buffer list. There is no Vulkan or dma-buf call for “only these two buffers on the ioctl.” Emptying the list unmaps dest (GPUVM fault). Process-wide ioctl rewrite killed RE2. A second Vulkan device on the same card shares the same drm client, so it is not a private list. CS-strip proved the list was the wait. CS-strip is not the fix and is not shipped (`launch_re.sh` has no preload).

Until Mesa submits capture with only the presented image and dest (dest still named), or the imported dest is truly explicit-sync, dma-buf will keep drawing the game and will not double.

Do not ship csstrip. leftover:none.
